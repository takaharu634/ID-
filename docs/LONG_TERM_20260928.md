## 使用方法

追加ツールはNode.js 22以上の標準機能だけを使います。追加のnpmパッケージやAPIキーは不要です。

```sh
# 更新を止めたデータ書き出しを、別の新規ディレクトリに保存
node tools/longevity/cli.mjs pack ./frozen-export ./backup-20260928

# 別の信頼できる場所に控えたmanifestのSHA-256で照合
node tools/longevity/cli.mjs verify ./backup-20260928 TRUSTED_MANIFEST_SHA256

# 既存データを上書きせず、新しいディレクトリへ復元
node tools/longevity/cli.mjs restore ./backup-20260928 ./restored-export TRUSTED_MANIFEST_SHA256

# 追加モジュールの試験
node --test tests/longevity/*.test.mjs

# 利用量の前提をJSONファイルに書いて試算
node tools/longevity/cli.mjs capacity ./capacity-assumptions.json

# 公開前の検証記録の不足・不一致を調べる（不適合なら終了コード2）
node tools/longevity/cli.mjs release-check ./release-evidence.json
```

容量試算の入力例:

```json
{"observedBytes":13132255,"observedSeasons":1,"years":20,"seasonsPerYear":2,"copies":3,"reservePercent":20,"budgetBytes":null}
```

これはCSV原本相当だけの仮定です。履歴の保存回数、分析用JSON、索引、データベース、ログ、動画、APIリクエスト料金は別に計上する必要があります。

公開前記録の入力項目は `observedPublishedCommit`、`basedOnPublishedCommit`、`sourceCommit`、`builtCommit`、`testedCommit`、`testsPassed`、`restoreDrillPassed`、`schemaVersion`、`deployedSchemaVersion` です。知らない値を推測で入力しないでください。

## バックアップの前提と安全性

- 元フォルダは更新を止めたエクスポートを使います。稼働中D1の一貫した書き出し、R2のスナップショット確定、クラウドからのダウンロードは、このツールの対象外です。個々のファイルの変更検出だけで、複数ファイルの同時点整合性は保証できません。
- 大きなファイルも小さなブロックで処理します。ディレクトリ一覧・索引等にも資源を使うため、メモリ・ディスク・時間に制約があります。無制限の容量を提供しません。
- 保存先は元フォルダの外、復元先はアーカイブの外を指定します。保存・復元先が存在すれば中止します。同一先への並行処理も抑止します。異常終了で `.lock` が残った場合は、他の処理が動いていないことを確認してから取り除いてください。
- 信頼できるローカルファイルシステムを前提とします。シンボリックリンク、危険な相対パス、特殊ファイル、展開サイズ異常は拒否します。信頼できない第三者が処理中にファイルシステムを差し替える環境での完全な隔離機構ではありません。
- ファイル内容・相対パス・空ディレクトリを保存します。更新日時、ACL、OS固有属性、実行権限は復元しません。
- gzipは暗号化ではありません。資格情報・APIキー・認証cookie・秘密の設定を同梱しないでください。データの閲覧権限に合う保存先を使い、共有範囲を広げないでください。
- アーカイブ内だけのハッシュは破損検出用です。故意の差し替え対策には、マニフェストのハッシュを独立した信頼先にも保管して、照合時に渡してください。
- 同じサービス内にコピーを増やすだけでは、アカウント喪失やサービス終了に十分備えられません。別の保存先や手元の保管も必要です。今回の処理にクラウド間の自動複製は含まれません。
- 成功時の読み戻し検査は実施しますが、ディスク故障・停電時の永続性、契約失効、運営終了を保証しません。

## 本番の長期運用に残っている作業

1. 最新の公開元ソースをGitHubへ同期し、本変更だけを取り込む。既存機能・データ・印刷・捕手/投手視点の仕様を維持して、型検査、ビルド、ブラウザー、印刷を確認する。
2. 保存版で固定されていた対応シーズン一覧と25,000球上限を、API・取り込み・画面・キャッシュのすべてで整合する方式へ改める。アーカイブツールには固定シーズンや行数制限を設けていないが、既存取り込み上限は変更していない。
3. 全季節・全履歴を毎回読む設計を避け、年度・シーズン・試合の索引、分割データ、必要部分の読み込み、集計結果の版管理へ統一する。元CSVの不変保存と従来の指標定義を維持する。
4. 入力変更通知を受けるイベント駆動取り込みを、実際のDrive認証・通知先・処理キューに接続する。同じ通知の再送や順不同に耐える識別子管理、再試行、検証後の公開版切替を行う。通知チャネル期限の更新と障害時の取りこぼし回復は別途必要。毎時のAI巡回は追加していない。
5. 本番R2・D1・設定の確定書き出し、独立先への複製、バックアップ失敗の通知、復元訓練を実環境に接続する。履歴削除は保持方針と復元可能性を確認してから行う。今回自動削除は追加していない。
6. 実際の契約容量・料金・利用量を確認し、予算と上限を決める。ストレージ・データベース・メモリ・処理時間・リクエスト数は別の制限として監視する。有料契約や増額を無断で行わない。
7. 個人レポートの固定URLと更新、複数年比較、検索条件保存、運用引継ぎは最新実装と重複を確認して統合する。選手が使うメニューや独自指標を無制限に追加しない。

目標は「通常のデータ追加や年度更新に開発を必要としない状態」です。セキュリティ対応、外部API変更、契約・権限の管理まで永久に不要になるとは説明しません。
